什么样的工作适合交给 AI

所有工作都应该用 AI、事事问 AI；这里说的是分工和价值。判断只看两个维度：是否需要智能（智能的本质是处理不确定性：需要理解、生成、判断、决策）× 结果是否可验证（有明确的目标、约束、验收标准，能判断做对没有）。

人主导 + AI 辅助

需要智能，但结果不可验证
  • 战略规划、创意发散
  • 复杂谈判、组织管理
  • 新业务探索
AI 给思路、资料和建议，最终由人判断和决策

AI 最佳场景

需要智能，且结果可验证
  • 评论 / 用户反馈分析
  • Listing 生成与优化
  • 广告异常诊断、选品分析
优先交给 AI，并沉淀为 Skill / Workflow / Agent

重新定义问题

不需要智能，且结果不可验证
  • 没有明确目标的日常工作
  • 职责不清、标准模糊的任务
  • 不知道什么叫"做好"
先把问题拆清楚，定义清晰的目标和标准

自动化

不需要智能，但结果可验证
  • 算利润、两列相加
  • 下载报表、格式转换
  • 定时任务、固定规则的审核
用代码 / 公式，更便宜、更稳定，别浪费 token

一句话：存在不确定性、需要智能处理，同时结果可以被验证。再进一步——高频重复，决定要不要沉淀成 Skill；多步骤协作，决定要不要做成 Workflow；需要持续感知、决策、行动，决定要不要做成 Agent。

和「团队 AI 上岗」里的挑活三筛不打架：三筛回答"这活值不值得交出去"，这两个维度回答"交给 AI，还是交给脚本"。

什么是 Skills

Skills 就是 Agent 的工作手册：业务流程、操作规则、判断边界、工具和验收标准的集合。如果说 Agent 是一名员工，Skill 就是他做某一类工作时用的标准作业手册，告诉他：什么情况下用这套能力、开工前检查什么、按什么顺序做、哪些步骤调脚本、哪些必须自己判断、遇到异常是继续还是停、最终交什么、达到什么标准才算完成。

一个 Skill 通常是一个独立文件夹，以 SKILL.md 为入口：

my-skill/ ├── SKILL.md # 入口：什么时候用、怎么做、怎么算做完 ├── references/ # 参考资料：规则、输出结构、异常处理 ├── scripts/ # 能算死的步骤，写成脚本 ├── templates/ # 固定的输出模板 └── examples/ # 做对的案例和做错的案例

Skill 不是"设计"出来的，而是从真实任务的执行、纠错、验证中逐渐演化出来的。

案例：一份 Listing 生成 Skill 是怎么长出来的

第一次，你只说了一句

"读取产品资料，分析关键词，然后生成 Title、Bullet Points、Description 和 Search Terms。"

Agent 交了活，你发现一堆问题，于是开始一条条补要求 →

补出来的 7 条

  1. 标题不要堆词，核心关键词放在前面（直播里的经验值：大致 75 字符以内）
  2. 不要只根据搜索量选词，还要判断关键词和产品的真实相关性
  3. 写卖点之前，先读 Review / VOC，确认消费者真正关心什么
  4. 竞品里出现的卖点不能直接照搬，必须确认我们的产品确实具备
  5. 尺寸、材质、兼容型号，只能从产品档案读取，不能自己推测
  6. 生成后先检查敏感词、商标词和夸大表述，通过后才输出最终版
  7. 最终必须同时输出 Listing、关键词埋词表和修改依据

于是，一条真正可用的任务流程逐渐形成：

读取产品档案
分析竞品
分析 VOC
筛选关键词
提炼卖点
生成 Listing
合规检查
埋词检查
输出最终结果

这些规则最初都散落在一次次聊天和纠错里。当这套流程已经过多个新品验证、以后每次上新都会重复用，就不该继续依赖聊天记录——把经过验证的流程、规则、工具和验收标准沉淀成一个「Amazon Listing 生成 Skill」。以后换一个产品、换一个对话、甚至换一个 Agent，都不用重新教一遍。它只要加载这个 Skill，就知道：拿什么资料 → 用什么工具 → 按什么顺序做 → 遵守什么规则 → 如何自检 → 最终交付什么。

一顿饱 → 顿顿饱：从一次对话，到稳定执行的任务。直播里给的经验线：一个任务你做了 3 次以上，就应该写成 Skills。

三个容易想错的地方，点开看

我这周末抽时间，把手上所有工作从 0 写成 Skills，行不行？
直播原话：第一种千万别干。上面那 7 条规则，没有一条是坐在那儿想出来的，每一条背后都是一次真实的翻车。从 0 手写，等于凭想象替未来的自己纠错——写出来的多半是正确的废话。先跑通真实任务，再把反复验证有效的做法沉淀下来。
第 5 条"尺寸、材质、兼容型号只能从产品档案读取"，为什么值得单独立一条？
因为这正是 AI 最容易编的地方。具体数字、规格、型号属于幻觉高发区，而 Listing 上写错一个兼容型号，换来的是退货和差评。所以这类信息不让它"分析"，只让它"照抄指定来源"——这就是手册里的判断边界：哪些它可以发挥，哪些一个字都不许动。
Skills 反复改了几轮，效果反而越来越差，怎么办？
别在原来的对话里继续修，直接新开会话重来。旧对话里堆满了互相打架的修改指令，越补越乱。把已经确认有效的规则带走，换个干净的会话重新搭，比在原地反复修正快得多。

我们刚才一起把「【任务名，如：为新品生成可上架的 Listing】」做完了。
这类任务我以后会反复做，请把这次对话沉淀成一个 Skill。

请这样做：
1. 回看整段对话，把我每一次纠正你的地方，逐条改写成规则。
   每条规则后面注明它来自哪一次纠错，方便我以后判断要不要保留。
2. 把最终跑通的做法写成有顺序的步骤。
   能用脚本或公式算死的步骤单独标出来，不要交给模型判断。
3. 写清判断边界：哪些信息只能从我指定的来源读取、不许推测；
   哪些地方你可以自己发挥。
4. 写清验收标准：交付哪几样东西，达到什么程度才算完成，你如何自检。
5. 按 SKILL.md + references/ + scripts/ + templates/ + examples/ 的结构组织，
   把这次的成品放进 examples/ 当作做对的案例。

拿不准的地方标「待确认」，不要替我编。

同事说："Skills 不就是长一点的提示词吗？我周末把我所有的活都写出来。"
请你劝住他，并告诉他什么时候才该动手写。

  • Skills 是工作手册，值钱的部分是判断边界和验收标准，不是字数
  • 每条规则背后都是一次真实纠错；从 0 手写等于凭想象，所以"千万别干"
  • 动手的时机：同一任务做了 3 次以上（经验值）、对业务有价值；其中不需要智能的环节交给脚本，不交给模型
练拿真活练一把直播作业 1
任务
梳理近三个月的工作，找出重复 3 次以上的，再从里面挑对业务有价值的（增收、降本、增效）。每一项过一遍上面的四象限。选 1 个落在"AI 最佳场景"的，做成你的第一份 Skills。
合格标准
清单不少于 5 项，每项标了象限和业务价值；选中的那一项有成型的步骤、至少 3 条来自真实纠错的规则、一条写得清的验收标准。
反馈闭环
用这份 Skills 再跑 2 次同类任务。每纠一次错，就补一条规则进去——它就是这么长大的。
衡量口径：同类任务里你需要纠错的次数，从 __ 次降到 __ 次；单次用时从 __ 到 __。
  • 近三个月的重复工作清单（不少于 5 项），逐项过四象限
  • 选定 1 个标的
  • 第一份 Skills 成稿（步骤 + 规则 + 验收标准）
  • 再跑 2 次，把新的纠错补进去

本页 Takeaway：先过两个维度，再决定交不交、交给谁；Skills 是从纠错里演化出来的工作手册，不是设计出来的；同一任务做了 3 次以上（经验值）且有业务价值就沉淀，别从 0 手写。
